# requests 与调度 / 超卖隔离（现象级）

- 维：C1｜题：R1-Q25｜挂钩：Q06、Q23、网易基架面经题感｜题源：2026-08-05
- 状态：**2026-08-09 口述**；**08-10 超卖隔离补答过关**；自测「乐观」主线对（纠：≠优先驱逐）

> 总句：**调度器看的是 requests（以及扩展资源），不是容器真实用量。** 不设 requests 时，调度常按「占地为 0」对待，容易把节点排满，真正打满时再靠 kubelet 驱逐/OOM——这是经典坑。

---

## 1. 调度看什么

```text
Filter：节点「可分配」是否 ≥ Pod requests（及其它硬约束）
  ——这里的「空余」= 按已调度 Pod 的 requests 扣减后的可分配，不是 top 瞬时空闲
Score：常按剩余资源等打分（策略可配）
真实 CPU 打满：调度当时可能仍觉得「放得下」
```

| 设置 | 调度直觉 | 风险 |
|------|----------|------|
| 合理 requests | 按预留占位 | 利用率可能偏低 |
| **不设 requests** | 近似 **0 占地** | 节点被塞爆 → 运行期抖/驱逐 |
| requests ≪ 实际 | 能调度上 | 运行期争抢、邻居受损 |
| 超卖（故意） | 提高利用率 | **必须**有隔离手段，不能只靠「调度能排上」 |

**不设 requests（面试一句）：** 调度几乎不占位 → 容易把很多「未知消耗」塞进同一节点 → 打满时伤邻居（你说的「榨干 node」）。

## 2. 「超卖隔离」到底在问什么？

不是再问一遍「cgroup 是什么」，而是：

> **用云原生手段尽可能规避异常/噪声负载拖死其他业务**（超卖或混部场景）。

| 手段 | 在隔离什么 | 一面怎么说 |
|------|------------|------------|
| **节点池 + 污点/亲和/容忍** | 在离线、敏感度分池，Pod 落对池 | 抽象层第一刀（你 08-10 口述） |
| **软反亲和** | 同业务/同组少扎堆一台物理机 | 降低单点互伤 |
| **合理 requests** | 占位尽量贴近真实用量 | 少「伪装很小」骗调度 |
| **cgroup / QoS / 离线降权** | 同机争抢时谁让谁 | 机制层刹车 |
| **PriorityClass + 抢占** | 高优上不去时挤低优 | 调度阶段让位 |
| **ResourceQuota / LimitRange** | 租户别把集群请求打爆 | 配额层 |

**学员过关级叙事：** 资源池（在离线/敏感）→ 污点/亲和落对 → 同业务软反亲和打散 → requests 尽量代表用量；再叠加 cgroup。

**对比：** cgroup = **同机运行期刹车**；池化/污点 = **尽量别坐一张椅子**。

## 2.1 「谁更乐观」= 谁按更宽松假设做事

| 阶段 | 谁更乐观 | 含义 |
|------|----------|------|
| **调度** | **更乐观** | 只按小 requests 占位 → 更容易判「放得下」 |
| **运行期** | **更险 / 不乐观** | 可突发到大 limits → 同机易争抢、抖、OOM |

**纠偏：** 小 requests ≠ 一定优先被抢占/驱逐。  
- 抢占看 **PriorityClass**；驱逐看 **QoS + 优先级** 等。  
- 有 requests 的 Burstable 通常仍比 BestEffort 更扛踢一点。  
一面句：**调度按小 requests 很乐观；险在运行期大 limits 打满邻居。**

## 3. 30 秒背板

> 调度按 requests 占位；不设近似 0 占地易塞爆。超卖隔离先讲池化/污点/反亲和与合理 requests，再讲 cgroup。requests≪limits：调度乐观、运行期险。

自测（已过）：limits 很大、requests 很小，调度和运行期谁更「乐观」？→ **调度更乐观。**
